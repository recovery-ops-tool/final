SYSTEM 01 — MULTI-TENANCY (ROW-LEVEL SECURITY)                    LAYER 0 · P0
--------------------------------------------------------------------------------
PREREQUISITES: none. This is the foundation.
DEPENDED ON BY: every system that reads or writes org-scoped data (all of them).

SHARED FILES — DO NOT EDIT CASUALLY (owned by this system):
  server/src/main/java/com/recoverpro/server/security/RlsAwareDataSource.java
  server/src/main/java/com/recoverpro/server/security/RlsDataSourceConfig.java
  server/src/main/java/com/recoverpro/server/security/RlsContextFilter.java
  server/src/main/java/com/recoverpro/server/security/RlsOrgIdHolder.java

CURRENT STATE [V]:
  Postgres Row-Level Security is the tenant boundary. RlsAwareDataSource (a
  DelegatingDataSource) stamps the `app.current_org_id` session GUC on every
  pooled connection checkout; RlsContextFilter populates the RlsOrgIdHolder
  ThreadLocal from the authenticated principal per request and clears it in a
  finally block. Platform-admin cross-org access goes through
  PlatformAdminAccessGuard.beginCrossOrgAccess() which sets a bypass flag and
  writes an audit row in a REQUIRES_NEW transaction.

  This is a genuinely strong design — stronger than the discriminator-column
  approach most SaaS apps of this size use, because a forgotten `WHERE org_id=?`
  cannot leak data. The weakness is coverage, not architecture: RLS was applied
  table-by-table over four migrations (V010, V040, V057, V058), each of which
  exists because the previous one MISSED tables and left them fail-OPEN. That
  pattern has repeated three times. There is no automated guard preventing a
  fourth.

PRODUCTION STANDARD 2026:
  Tenant isolation is enforced at the storage layer (RLS or equivalent) AND
  continuously verified by an automated test that fails CI when any org-scoped
  table lacks a policy. Isolation is never "we remembered to add it" — it is
  "the build breaks if we forget."

GAP:
  No automated coverage test. A new org-scoped table added next month ships
  fail-open and nothing catches it.

TASK 1.1 — Automated RLS coverage guard                                    [P0]
  Layers: test
  a. Create server/src/test/java/com/recoverpro/server/security/
     RlsCoverageTest.java as an @SpringBootTest against the real test database
     (the project already has Testcontainers/test-DB wiring — reuse whatever
     the existing integration tests use; find one with
     `grep -rln "@SpringBootTest" server/src/test/java | head -5`).
  b. In the test, query the catalog for every table that has an
     `organization_id` or `org_id` column:
       SELECT c.relname FROM pg_class c
       JOIN pg_namespace n ON n.oid=c.relnamespace
       JOIN pg_attribute a ON a.attrelid=c.oid
       WHERE n.nspname='public' AND c.relkind='r'
         AND a.attname IN ('organization_id','org_id') AND a.attnum>0;
  c. For each such table assert BOTH `relrowsecurity` AND `relforcerowsecurity`
     are true in pg_class, and that at least one row exists in pg_policy for it.
  d. Maintain an explicit, commented ALLOWLIST set in the test for tables that
     are intentionally global (there is at least one: the RAG document library
     from V032 is platform-wide by design and correctly has no RLS — its
     migration comment says so). Every allowlist entry needs a one-line reason.
     An unexplained entry is a bug, not an exemption.
  e. Fail the test with a message naming the offending table(s).
  ACCEPTANCE: `mvn -f server/pom.xml test -Dtest=RlsCoverageTest` passes today,
  and fails if you temporarily create a scratch table with an organization_id
  column and no policy (verify this by actually doing it, then dropping it).

TASK 1.2 — Verify partitioned-table policy inheritance                     [P1]
  Layers: migration / test
  a. Partitioned tables (user_action_audit_logs, unified_audit_events) declare
     RLS on the PARENT. Confirm Postgres actually enforces parent policies on
     each partition for the version in use — write a test that inserts a row for
     org A, sets app.current_org_id to org B, and asserts the row is invisible
     when queried through BOTH the parent table and the partition directly.
  b. If querying a partition directly bypasses the parent policy, add explicit
     per-partition RLS in a new migration AND extend PartitionMaintenanceJob to
     apply it to every future partition it creates (see SYSTEM 10, TASK 10.2 —
     that job currently only handles one table).
  ACCEPTANCE: a direct `SELECT * FROM unified_audit_events_2026_08` under org B's
  GUC returns zero of org A's rows.

TASK 1.3 — Bypass-flag blast-radius test                                   [P0]
  Layers: test
  a. Read PlatformAdminAccessGuard.java and RlsOrgIdHolder.java. Confirm the
     bypass flag is cleared in a finally block on every exit path including
     exceptions.
  b. Write a test that calls beginCrossOrgAccess(), throws inside the block, and
     asserts that a subsequent unrelated query on the SAME THREAD is back under
     normal org scoping. A leaked bypass flag on a pooled request thread is a
     total tenancy failure — this test is the only thing standing between you
     and that.
  c. Assert the same for beginUnattendedCrossOrgAccess().
  ACCEPTANCE: both tests pass; deliberately removing the finally-block clear
  makes them fail.

--------------------------------------------------------------------------------
PREREQUISITES: none.

CURRENT STATE [V]:
  Flyway, 90 sequential versioned migrations (V001..V090), no repeatable
  migrations, no undo scripts. Migrations run automatically on application
  startup. Several migrations exist purely to fix earlier ones (V040, V057, V058
  all patch RLS gaps left by V010) — which is honest history, but shows there is
  no pre-merge validation catching those gaps.

PRODUCTION STANDARD 2026:
  - Migrations validated in CI against a scratch database before merge.
  - Expand/contract discipline: no migration both adds and destroys in one step;
    destructive changes are a separate, later migration after code has shipped.

    explicit, documented maintenance window.
  - Migration runs are observable — you can tell from logs/metrics which version
    a running instance is on.

GAP:
  No CI validation step. Auto-migrate-on-startup means a bad migration takes the
  app down at boot across every instance simultaneously. No documented rollback
  procedure.

SYSTEM 04 — ENVIRONMENT & CONFIGURATION MANAGEMENT                LAYER 0 · P1
--------------------------------------------------------------------------------
PREREQUISITES: none.

CURRENT STATE [V]:
  Spring Boot externalized config via application.properties with ${ENV_VAR:default}
  placeholders throughout. JwtTokenProvider validates its secret at startup and
  refuses to boot on a blank, placeholder, or under-256-bit value — this is
  genuinely good practice and should be the model for every other secret.
  server.forward-headers-strategy=native and
  server.tomcat.remoteip.internal-proxies=${TRUSTED_PROXY_CIDR:} are correctly
  configured, giving proper trusted-proxy client-IP resolution at the Tomcat
  layer. (Note: three application-level methods bypass this correct mechanism —
  that is SYSTEM 08's problem, not this one.)

PRODUCTION STANDARD 2026:
  - Secrets come from a secret manager, never from a .properties file or a
    plaintext env file on disk.
  - Startup fails loudly on any missing required config, in every environment.
  - Config is documented: one authoritative list of every env var, whether it is
    required, and what happens if it is absent.
  - No production default that is silently insecure.

GAP:
  Secrets are env vars with defaults. Several ${VAR:} defaults are empty strings,
  which means a missing value produces a subtly broken runtime rather than a
  loud startup failure. There is no single documented env-var inventory.

CURRENT STATE [V]:

  revoked role or a deactivated user continues to be honoured from cache until

  a. Re-confirm first:
     grep -rn "evictUserCache" server/src/main/java

     identity, roles, permissions, or active status. The count was seven at
     audit time; verify against current code since UserServiceImpl gained 64

SYSTEM 26 — SEARCH / FILTER / SORT INFRASTRUCTURE                 LAYER 2 · P0
--------------------------------------------------------------------------------
PREREQUISITES: SYSTEM 07 (encryption understanding) done. Read SYSTEM 07's
CURRENT STATE before starting — this system's central bug is an encryption
interaction and you cannot fix it correctly without understanding
LookupHashService.

CURRENT STATE [V]:
  JPA Specifications drive filtering (PtpSpecification and siblings), with
  Pageable sorting and PagedResponse.

  CONCRETE BUG [V] — THE BORROWER NAME FILTER IS PERMANENTLY BROKEN.
  PtpRecord.borrowerName is annotated
  @Convert(converter = EncryptedStringConverter.class), so the column holds
  AES-256-GCM ciphertext with a random IV per row. PtpSpecification.withFilters()
  executes:
      cb.like(cb.lower(root.get("borrowerName")), ...)
  A LIKE against ciphertext can never match. Worse, because each row has a random
  IV, two identical names produce different ciphertext — so even an exact-match
  comparison would fail. The filter silently returns zero results and reports no
  error. A user searching for a borrower concludes the record does not exist.

  This is not a missing feature; it is a feature that appears to work and does
  not. It is the single most user-visible defect found in the entire audit.

  The codebase ALREADY has the correct mechanism: LookupHashService computes
  HMAC-SHA256 blind indexes, including name-PREFIX tokens specifically so that
  prefix search over encrypted names is possible. It is simply not used here.

PRODUCTION STANDARD 2026:
  Searchable-encryption via deterministic blind indexes for equality and prefix
  matching; anything richer (fuzzy, full-text) requires a separate index that is
  itself access-controlled.

TASK 26.1 — Fix encrypted-field search                                     [P0]
  Layers: entity / migration / service / repository / specification / web
  a. Read security/encryption/LookupHashService.java in full and understand the
     existing name-prefix token scheme before writing anything.
  b. Add a blind-index column to PtpRecord (e.g. borrower_name_prefix_hash) in a
     new migration, indexed for lookup.
  c. Populate it on write: wherever borrowerName is set, compute and store the
     prefix token(s) via LookupHashService. Find every write path — creation,
     import, Lucien tools, manual edit. Missing one write path means partially
     broken search, which is harder to diagnose than fully broken search.
  d. Backfill existing rows in the migration or a one-shot job. The backfill must
     decrypt each row to compute the hash — it therefore must run with the
     encryption context available, which means it is an application-side job,
     not pure SQL. Plan accordingly and make it resumable.
  e. Rewrite PtpSpecification.withFilters() to match on the hash column instead
     of LIKE-on-ciphertext.
  f. Constrain the UX honestly: blind indexes support prefix/exact match, not
     substring or fuzzy. If the UI implies "contains anywhere", change the UI
     copy to "starts with" rather than shipping a search that silently misses.
  g. Apply the identical treatment to EVERY other encrypted field used in a
     filter. Search for the pattern:
     grep -rln "EncryptedStringConverter" server/src/main/java/com/recoverpro/server/entity
     then for each such entity, check its Specification class for LIKE/equal
     predicates on those fields. Expect Allocation, Collection, and Visit
     entities to have the same problem.
  h. Add a test per fixed field asserting a real search returns the expected row.
  ACCEPTANCE: searching a known borrower's name prefix returns that borrower on
  every affected entity; a test would fail if the LIKE-on-ciphertext pattern

PREREQUISITES: SYSTEM 07 (encryption) and SYSTEM 25 (storage) done.

CURRENT STATE [V]:
  A well-designed flexible import pipeline: an EntityImportProcessor interface
  with an ImportContext and concrete processors (AllocationImportProcessor,
  CollectionImportProcessor, PtpImportProcessor, VisitImportProcessor), driven
  by a customer-configurable ColumnSchema so each org can map its own file

  ExportServiceImpl calls auditService.record().

  CONCRETE BUG [V] — PII IS DUPLICATED IN PLAINTEXT.
  Allocation.dynamicData is a plain JSONB column
  (@JdbcTypeCode(SqlTypes.JSON), no encryption converter). AllocationImportProcessor
  populates it with the ENTIRE raw uploaded row via
      new LinkedHashMap<>(row)
  That row includes borrower_name, phone, email, and ckyc_id — the exact fields
  that are carefully AES-256-GCM encrypted in their own dedicated columns on the
  SAME entity. So every encrypted field also exists, unencrypted, in the JSONB
  column beside it.

  This defeats the entire encryption-at-rest design for imported data, which is
  most of the data in the system. Anyone with database read access — a backup, a
  replica, a compromised credential, a support query — sees the PII in clear.

PRODUCTION STANDARD 2026:
  - Large imports are streamed, chunked, resumable, and progress-reported.
  - Validation happens before commit with a per-row error report.
  - Exports are async, access-controlled, audited, and time-limited.
  - Encryption posture is uniform: a field is either protected everywhere or it
    is not protected at all.

TASK 35.1 — Stop duplicating PII into plaintext JSONB                      [P0]
  Layers: entity / service / migration
  a. Re-confirm the finding: read AllocationImportProcessor and locate the
     `new LinkedHashMap<>(row)` assignment into dynamicData, then read
     entity/Allocation.java and confirm dynamicData carries no encryption
     converter while borrowerName does.
  b. Determine what dynamicData is legitimately FOR — carrying org-specific

     column. The ColumnSchema already knows the mapping — use it as the

  d. Apply the same check to the other three processors (Collection, Ptp, Visit).

     only Allocation is affected.
  e. BACKFILL: existing rows already contain plaintext PII. Write a one-shot job
     that strips those keys from existing dynamicData values. This is the part
     that actually remediates the exposure; fixing only the forward path leaves
     every existing record exposed.
  f. If any remaining dynamicData content can still contain PII (an org maps an
     unmapped column containing a phone number), the honest fix is to encrypt

  g. Add a test asserting no encrypted field's plaintext value appears in

  ACCEPTANCE: after importing a file containing borrower name, phone, email, and

SYSTEM 41 — BACKUP & DISASTER RECOVERY                            LAYER 4 · P0
--------------------------------------------------------------------------------
PREREQUISITES: SYSTEM 05 (infra known) done.

CURRENT STATE [?]:
  Not verified. No backup configuration was found in the repository. If the
  database is managed, automated backups may exist by default — but default
  backups that have never been restored are not a recovery capability, they are
  an assumption.

PRODUCTION STANDARD 2026:
  - Automated backups with defined RPO and RTO.
  - Point-in-time recovery.
  - Restores TESTED on a schedule. An untested backup is not a backup.
  - Backups encrypted, access-controlled, and stored separately from the primary.
  - A written, rehearsed DR runbook.

GAP:
  This is the highest-consequence unknown in the entire tasklist. Every other
  system's value is contingent on the data still existing. Treat it as P0 even
  though nothing is currently broken.

TASK 41.1 — Establish the current backup position                          [P0]
  Layers: investigation / docs
  a. Determine, from the actual deployment: are automated backups running? What
     is the schedule, retention, and storage location? Is PITR enabled? Are
     backups encrypted? Who can access them?
  b. Record the answers in docs/RUNBOOK-DR.md. If the answer to any of these is
     "unknown", that is the finding — write it down and escalate.
  c. Do not proceed to 41.2 on assumptions.
  ACCEPTANCE: the current position is documented factually.

TASK 41.2 — Define and meet RPO/RTO                                        [P0]
  Layers: config / docs
  a. State the targets explicitly. For a financial-recovery product handling
     customer collections data, an RPO measured in minutes (PITR) and an RTO
     measured in a few hours is a defensible starting position — but the number
     must be a decision, not a default.
  b. Configure backups to meet the RPO: PITR/WAL archiving for the database,
     versioning and cross-region replication for object storage (SYSTEM 25 —
     file data is customer data too and is often forgotten in DR planning).
  c. Verify Redis: determine what is stored there that cannot be reconstructed.
     ShedLock state and caches are reconstructible; PendingAction confirmation
     tokens and rate-limit counters are transient. If anything durable lives
     only in Redis, it needs a backup or needs to move.
  ACCEPTANCE: configured backup frequency demonstrably meets the stated RPO for
  both database and object storage.

TASK 41.3 — Test the restore                                               [P0]
  Layers: ops
  a. Actually perform a full restore into an isolated environment. Not a
     tabletop — a real one.
  b. Measure the elapsed time and compare against the RTO. Most first restores
     take dramatically longer than expected; that number is the point of the
     exercise.
  c. Verify the restored data is complete and usable: run the application
     against it, confirm RLS policies and triggers survived the restore (a
     restore that loses the immutability triggers or RLS policies is a security
     regression), and confirm encrypted data is still decryptable — which means
     verifying the encryption key is available in the DR environment. A perfect
     backup with an unavailable key is worthless.
  d. Record the results and the actual procedure in docs/RUNBOOK-DR.md.
  e. Schedule this to repeat quarterly.
  ACCEPTANCE: a documented, timed, successful restore including RLS policy
  verification and encrypted-field decryption.

TASK 41.4 — DR runbook                                                     [P1]
  Layers: docs
  a. Write the full procedure: detection, decision authority, communication plan
     (including customer notification), step-by-step recovery, and validation
     checklist.
  b. Include partial-failure scenarios, not just total loss: one corrupted
     table, an accidental mass delete, a bad migration in production.
  c. For the accidental-delete case specifically: PITR to just before the
     incident is the answer, which means knowing the exact time — another reason
     the audit trail matters.
  ACCEPTANCE: the runbook covers total loss, partial corruption, and accidental
  deletion, and names a decision-maker for each.

TASK 42.1 — Require a reason for cross-org access                          [P1]

     non-blank reason and record it. The CROSS_ORG_ACCESS action already exists
     in the enum.
  b. Unattended (background job) access records the job name as its reason
     automatically — do not force a human-style reason there, but do distinguish
     the two clearly in the audit row.
  c. A reason field that is optional will be empty. Make it mandatory at the
     method signature level so it cannot be skipped.
  ACCEPTANCE: cross-org access without a reason fails to compile; every
  CROSS_ORG_ACCESS audit row has a non-empty reason.

     what they did during the session (correlate via correlationId — the column
     exists and is indexed for exactly this).

  c. Web: a platform-admin access-review page.
  d. Unreviewed admin access is how insider incidents go undetected for months.
  ACCEPTANCE: the report shows every cross-org session with its reason and the
  actions taken within it.
